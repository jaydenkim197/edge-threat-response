## GPU 처리량과 배치 검증

공통 [벤치마크](../tools/benchmark_yolo_training.py)는 YOLO26n·640·1 class·FP32(TF32 끔)의 CUDA NMS, forward, loss, backward, AdamW step을 테스트한다. 같은 seed, GPU 생성 텐서, 2 warm-up + 6 timed step, 배치별 중앙값을 사용했다. 학습 입력을 서버로 보내지 않고 10개 GPU에서 서로 다른 노드의 성능을 확인했다. 결과 표는 [합성 벤치마크 기록](training-gpu-benchmark-2026-11-26.md)에 둔다. 실제 로더·타일·검증·IO는 별도로 측정한다.

- 배치마다 물리 UUID, driver/runtime·torch/vision, 모델·해상도·정밀도, imgs/s·p50/p95 step, 최대 VRAM과 남은 VRAM을 기록한다. 합성 값에서 여유가 있는 배치를 출발점으로 잡고, 승인된 동일 개발 자료에서 로더·증강·validation을 포함한 최소 100 update와 validation 1회를 연속 시험한다. 장시간 대표 부하에서도 오류·메모리 증가·열 제한이 없고 관측 VRAM 여유가 **1 GiB 이상, 전체의 10% 이상**이면 그 조건의 안정 배치로 기록한다. 위 기준으로 가장 큰 검증 배치와 처리량 대비 효율적인 운영 배치를 각각 기록한다.
- 재현 비교는 기존 배치와 샘플 순서를 고정한다. 메모리 한계로 batch나 AMP를 바꾸면 optimizer updates, accumulation/nbs, LR, BN 차이를 따로 표시한다. 배치가 맞기 전까지 그룹 비교를 임의로 합치지 않는다. 다른 호스트에서 재개하는 경우 runtime 차이와 재현성 기준을 기록한다. bitwise 동일성이 필요한 실행은 같은 호스트와 스택을 사용한다.

## 서버 동시 실행 상한 측정

초기에는 연구실 서버에서 **한 작업씩** 실행하고, PC11~14의 독립 실행을 병행한다. 연구실 서버의 카드별 전력 제한 합은 **1,840 W**다. 이 값은 실제 사용량이나 PSU·콘센트 허용치가 아니다. 연구실에서 PSU·전원 회로·냉각 여유를 확인하고, 확인된 조합으로 1→2→4→최대 6개 순으로 늘린다. 단계별 동일 입력을 단독과 10~15분 혼합 부하에서 비교하고 실제 작업 집합의 완료 예상 시간이 줄어드는 조합만 유지한다.

| 관측 | 수집 | 배정 규칙 |
| --- | --- | --- |
| GPU·열·전력 | `nvidia-smi`로 카드별 1초 온도·클록·VRAM·전력·사용률 및 thermal/power limit 이유. `sensors`로 CPU 온도 | 열 제한, 지속 클록 하락, 확인한 전력 한도 접근 시 신규 배정을 중지한다. 냉각 후 안정 조합으로 돌아간다. |
| CPU·RAM | `vmstat 1`, 프로세스별 RSS·CPU, `/dev/shm`, swap 및 dataloader wait | 각 작업 workers=2부터 측정한다. CPU 대기나 RAM/swap 압박으로 처리량이 떨어지면 동시 실행 또는 workers를 낮춘다. |
| 저장장치·데이터 | `/proc/diskstats` 차분, `vmstat` iowait, 가능하면 `iostat`, 데이터 준비·체크포인트 쓰기 시간 | 승인 입력을 한 번만 스테이징하고 읽기 공유한다. 장시간 증강, 자료 전송, 체크포인트 회수는 I/O 병목 시 겹치지 않게 한다. |

## 대기열·동적 배정·실패 복구

초기 11/26 학습은 독립 원격 프로세스로 실행했고, 이후 [야간 큐](p430-overnight-queue.md)에서 완료 영수증을 받아 지정 호스트별 우선순위로 후속을 시작한다. 아래는 후속 확장 시 적용할 계획이다. Windows에서 승인된 VPN/SSH 경로로 양쪽을 조회한다.

1. **대기열과 배정.** 작업마다 `job_id`, 트랙, 선행 작업, 입력/설정/commit SHA, 필요한 VRAM·런타임, 계획 update 수, 상태, 우선순위를 둔다. 준비된 작업 중 마감까지 선행 경로가 가장 긴 작업을 우선한다. 장비는 가용 시각에 데이터 전송·실측 처리량·평가·결과 회수 시간을 더해 가장 빨리 완료하는 호스트로 선택한다. 3090이 필요한 작업이 대기할 때는 적합한 3060/3080가 가벼운 작업을 가져간다. GTX 1080 Ti는 같은 부하 상한에서 전체 종료가 빨라질 때 사용한다. DDP는 단일 GPU 대비 실제 단축과 유효 배치 일치가 확인될 때만 검토한다.
2. **충돌 방지.** 하나의 배정 기록을 원자적으로 갱신하고, 실행 호스트에서 `host+GPU UUID` 단위 GPU 잠금과 작업 키 잠금을 확보한다. 점유 재조회 후 해당 UUID만 노출한다. 상태에는 PID와 시작 시각, 최근 heartbeat, run/attempt 경로, 마지막 checkpoint SHA를 기록한다. SSH가 끊기면 상태를 미확인으로 두고 원격 PID·잠금·영수증을 대조한 뒤 배정을 재개한다. heartbeat만으로 슬롯을 해제하거나 다른 사용자의 프로세스를 종료하지 않는다.
3. **자동 복구 경계.** 일시적 연결/프로세스 중단은 소유 실행이 끝났음을 확인한 뒤 동일 설정과 검증한 resume 체크포인트로 한 차례 재실행한다. 평가 실패는 학습을 보존하고 평가 작업만 재실행한다. OOM은 같은 비교 조건을 만족하는 더 큰 여유 GPU가 있으면 1회 재배정한다. 배치를 줄이거나 정밀도를 바꿔야 하면 별도 profile/run으로 비교한다. 데이터·해시 불일치, NaN, 반복 OOM, 권한 오류는 원인과 원래 로그를 남기고 보류한다. 사용자 환경에 없는 재부팅 자동 실행은 연구실 정책 확인 후 추가한다. [Ultralytics resume](https://docs.ultralytics.com/modes/train/#resuming-interrupted-trainings)
4. **로그와 체크포인트.** 승인 릴리스 `data/releases/<sha>`는 읽기 전용으로 공유하고, `runs/<track>/<job_id>/attempt-<n>/`에 profile·manifest/commit SHA, 환경 freeze, GPU 로그, stdout/stderr, heartbeat·exit 영수증, `results.csv`, 검증 지표를 둔다. 중간 저장점은 optimizer·scheduler 상태와 step 확인 후 `resume`으로 승인한다. 임시 파일을 완성한 뒤 경로를 바꾸고 검증 SHA가 기록된 결과만 수집한다. 실패 attempt는 보존하고 평가 결과와 주요 가중치는 PC13에 해시 대조 후 회수한다.
