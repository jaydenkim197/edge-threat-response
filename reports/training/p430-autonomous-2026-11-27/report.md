# P430 자율 연구 1차 결과

2026-11-27 KST · [자율 연구 기준](../../../docs/autonomous-research-plan.md) · [직전 야간 비교](../p430-overnight-2026-11-27/report.md)

**D1·MIX70 결합은 전체 검출이 늘었으나 음성 오탐 기준을 통과하지 못했다.** D1을 개발 기준선으로 유지한다. 후속 실험은 MIX70에서 반복적으로 잘못 검출된 음성을 학습 구간에서 찾고, 같은 자료 구성에서 음성 예제만 교체하는 방향으로 진행한다.

## A-FUSION-P0 · PC13 CPU

기존 가중치의 저장 예측을 사용했다. D1과 MIX70은 PC13, seed 3409는 PC12 결과다. 완료 영수증·모델·예측 SHA를 대조했고, 승인된 계획에서 이미지·라벨과 평가 분할을 재검증했다. 개발 확인셋 287장 중 작은 칼 정답은 58개, 전체 칼 정답은 140개, 음성 프레임은 147장이다. 운영점은 튜닝셋 298장에서 음성 프레임 오탐 1장 이하로 선택했다.

후보 네 가지는 D1에 MIX70 또는 seed 3409를 결합하는 NMS·일치 점수 방식이다. 일치 점수 방식은 다른 모델과 IoU 0.40 이상의 후보가 겹치지 않으면 점수에 0.50을 곱하고, 기존 NMS IoU 0.55를 적용한다. 튜닝 결과에서 후보 하나와 임계값을 선택해 공통 개발 확인셋에 한 번 적용했다. 다른 세 결합 방식은 확인셋에서 평가하지 않았다. [평가기](../../../tools/p430_dev_fusion.py)

| 개발 확인셋 조건 | 작은 칼 / 58 | 전체 / 140 | 음성 오탐 / 147 | FP 박스 | AP50 | AP50–95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| D1 | 47 | 81 | 0 | 23 | 61.82% | 18.04% |
| MIX70 | 48 | 97 | 7 | 24 | 71.72% | 25.87% |
| D1 재현 seed 3409 | 50 | 91 | 3 | 36 | 67.07% | 18.33% |
| D1 + MIX70 · 일치 점수 | 45 | 88 | 5 | 33 | 69.57% | 24.08% |

선택된 일치 점수 방식의 튜닝 임계값은 0.3689592779였다. 튜닝에서 작은 칼 96개·전체 125개·음성 오탐 1장을 기록했고 MIX70 단독은 각각 98개·129개·1장이었다. 단순 후보 결합은 현재 데이터의 점수 분포 차이를 해결하지 못했다. 개발 확인에서는 작은 칼 목표까지 8개, 전체 목표까지 24개가 부족했고 허용 오탐을 4장 초과했다.

`A-FUSION-P0/attempt-01` 완료 영수증의 `result.json` SHA-256은 `8792941711945684c21c80be1de19d8aaa4472e799d13bb92190f77b8e67b056`이다. 레거시 앙상블 중계에서 잘못 조회하던 개발 예측 파일명도 수정했다. 개발 파일은 `.pt.jsonl`, 튜닝 파일은 `.jsonl`이다. 신규 평가 작업은 PC14에 의존하지 않는다. [큐 등록](../../../configs/training/p430-overnight-queue.json)

## 후속 실험과 재개 지점

- `A-MIX70-NEG-MINE`은 PC12에서 중앙 영역의 기존 사람 검수를 통과한 학습 음성 422장을 파일 해시 및 빈 라벨과 대조하고, MIX70 점수 0.15 이상인 34장을 찾았다. 같은 녹화에서 5초 간격을 적용해 18장(11/17 5장, 11/19 13장)을 추렸다. 3장은 근처 시각에서 겹치는 검출도 있었다. 완료 영수증 SHA-256은 `692e7abde5adf7b512743c78671a0741a6142204e0a8c962b9519776c5d9ef0b`다. [후보 수집기](../../../tools/p430_train_hard_negatives.py)
- PC12의 `A-MIX70-NEG-TRAIN`은 전처리 상수 import 누락으로 학습 전에 종료했다. 원래 실패 영수증을 보존하고 import를 고쳐 `A-MIX70-NEG-TRAIN-R1`을 등록했다. D0 초기값·seed 3407·배치 8·12 epoch·출처별 5,734/1,638/820회 추출·48% 타일을 유지한다. 같은 촬영의 일반 전체 화면 음성에서 약 5%를 교체하며 후보 1장당 epoch에 최대 5회 추가한다. 실행 계획에서 epoch당 59~61회 동수 교체와 실제 작업 프로세스를 확인했다. 기존 중앙 영역 검수 결과를 라벨 근거로 사용했다. 비교 주 지표는 튜닝셋 임계값을 적용한 공통 개발 확인셋 6타일 결과다.
- 연구실 RTX 3090 물리 번호 2에서 `A-P430-ONLY`의 첫 epoch 배치 진행을 확인했다. D0와 동일 추출량·48% 타일을 유지하고 P430 외 학습 출처를 제거하는 대조다. 같은 두 촬영의 반복 노출과 출처 일반화 손실을 함께 확인한다. 연구실 서버의 한 작업 동시 실행 기준을 적용했다.
- `B-ALT01-CROP-PILOT`은 PC13의 CPU Worker에서 MIX70 크롭 재검증을 비교하도록 등록했다. 기존 중앙 영역 검수 학습 자료로 HOG 분류기를 학습하고 튜닝셋에서 MIX70 자체 점수를 대조군으로 사용한다. 소형·전체 검출을 유지하고 오탐이 감소하는 후보만 개발 확인에 적용한다. PC13의 기존 GPU 작업은 건드리지 않는다. [크롭 검증기](../../../tools/p430_crop_verifier.py)
- PC14에는 사용자 지시에 따라 18:00 KST 전까지 접속하지 않는다. 11/24 최종 독립 평가 자료는 이번 연구의 학습·튜닝·검증 경로에 반입하지 않았다.

## Orin 파일 실측과 동결 시점

같은 Orin Nano 25W 모드와 승인된 개발 프레임 24개를 사용했다. D1 가중치·임계값 0.2883733511을 유지하고 6타일의 BGR 입력 준비에서 복사를 줄였다. Ultralytics 8.4.152에서 입력 텐서가 기존 방식과 일치했고 Orin에서 전후 모두 13개 프레임에 13개 박스를 보였다. 4K 좌표로의 이동(960, 540)을 실제 CUDA 출력에서 검증했다. PyTorch 2.14.1+cu132에서 입력 변환과 검출·병합을 포함한 p95는 **252.1 → 152.2ms**, 최적화 후 중앙값 143.1ms, 최대 Torch 할당 182.9MiB였다. 같은 보드의 기존 실험용 검출 경로는 p95 149.3ms였다. [타일 검출기](../../../src/edge_threat_response/p430_tile_detector.py)

같은 24개 개발 JPEG를 디코딩하고 COCO YOLO26n 사람 검출·D1·B3·모의 경보까지 연결했다. 유효 24장, 사람 검출 13장, 칼 검출 13장, 모의 경보 1건, 처리 오류 0건, p95 **257.5ms**였다. 별도 짝 비교에서 사람 검출만 FP16으로 바꾸면 34개 사람 박스가 모두 IoU 0.90 이상으로 대응했고 최소 IoU는 0.9685였다. 같은 프레임에서 모의 경보가 발생했으나 전체 p95는 FP32 267.2ms에서 FP16 276.1ms로 늘어 사람 경로 FP32를 유지한다. 두 파일 실측은 RTSP J 평가와 별개다. Orin의 `runs/p430-goal-runtime-20261127/`에 결과·프로필을 보관한다.

OpenCV에서 JPEG를 BGR 배열로 직접 읽는 별도 파일 비교에서 사람 입력 640의 전체 p95는 **229.0ms**, 512는 **225.7ms**였다. 칼 검출 13장과 모의 경보 프레임은 일치했다. 512에서는 기존 사람 박스 34개가 IoU 0.75 이상으로 대응했고 사람 박스 2개가 추가됐다. 지연 이득 3.3ms와 검출 변화가 관측돼 640 FP32를 실시간 검증 기준으로 유지한다. 이 결과는 같은 24개 개발 JPEG의 파일 실측이며, 실제 RTSP 디코딩과 4Hz 장시간 운용의 증거는 별도다. 결과는 Orin의 `runs/p430-goal-runtime-20261127/person-size-pilot/result.json`에 보관한다.

P430의 저장된 RTSP 포트는 TCP 시간 초과였고 20.3초 수신 검사에서 0프레임이었다. 실제 운영 J 검증은 4K 주 스트림, Orin 25W, **4.0Hz 목표 샘플링(주기 250ms)**을 기준으로 진행한다. 사람 검출·판단·경보·디코딩을 포함해 60초 예열과 10분 세 번의 무중단 실행, 유효 3.8FPS 이상, 샘플 누락률 5% 이하, 처리 p95 250ms 이하 및 RAM·지연·큐 안정성을 측정한다. 파일에서 얻은 위 검출 지연은 J 통과 증거와 분리한다. [J 배포 기준](../../../docs/p430-track-b-alternative-detection-plan.md#4-공통-검증-방법과-통과-기준)

안정성의 허용 편차는 공유 RAM 64MiB와 지연·큐 대기 p95 10ms로 두었다. Orin에서 측정기의 CLI 기동을 확인했다. 측정기는 프레임을 저장하지 않고 사람 검출·판단·모의 경보 및 메모리 내 JPEG 인코딩을 계측한다. 물리 경보와 디스크 기록 지연은 별도 검증이 필요하다. 사용자의 지시에 따라 카메라 현장 연결 확인은 마지막 통합 검증으로 둔다. [실측 도구](../../../tools/p430_orin_j_benchmark.py)

마감 전 필수 평가·제출 시간을 확보하기 위해 **11/29 12:00 KST**를 후보 결정 시점으로 둔다. 새 후보가 성능과 재현성 및 J 기준을 충족하지 못하면 D1을 독립 평가 후보로 동결한다. 독립 평가 자료는 동결 이후 승인된 절차에서만 열며, D1 동결은 연구 성능 목표 달성과 구분한다.

## B-ALT01-CROP-PILOT 결과

PC13의 CPU Worker가 학습 이미지 761장에서 기존 검수 라벨을 바탕으로 양성 후보 326개, 음성 후보 460개를 학습했다. 같은 튜닝셋에서 MIX70 단독은 작은 칼 98개, 전체 129개, 음성 오탐 1장, FP 박스 12개였다. HOG 결합 가중치 0.25는 이 수치가 같았고 AP50이 84.97%에서 84.79%로 낮아졌다. 가중치 0.50은 작은 칼 97개, 전체 128개에 음성 오탐 1장과 FP 박스 12개였다. 두 조건 다 승격 기준에 미달해 개발 확인셋 평가를 실행하지 않았다. 완료 영수증 SHA-256은 `fdda3664fe22991099eb3f702eb5b452bf408c317561e879ec9ed230bafd5c57`이다.

다음 비교는 PC12 `A-MIX70-NEG-TRAIN-R1`과 연구실 `A-P430-ONLY`의 완료 영수증에서 재개한다. 튜닝에서 고른 한 운영점을 고정한 채 소형·전체 검출 수, 음성 오탐, AP 두 지표를 공통 기준에 대조한다. PC14는 11/27 18:00 KST 이후 접속 상태부터 확인한다.

## B-ALT02-BACKGROUND-PILOT 결과

PC13 CPU에서 MIX70이 기존 학습 음성의 같은 녹화에서 반복 탐지한 위치 3건을 사용했다. 녹화 하나에서 나온 약 두 위치다. 고정 중앙 크롭 좌표에서 IoU 0.50 이상 겹치는 후보의 confidence를 0.75 또는 0.50배로 낮추고, 튜닝에서 검출 수를 보존하면서 오탐을 줄일 때만 확인셋으로 넘어가는 규칙을 사전에 적용했다. 튜닝 프레임 298장의 어떤 검출도 이 위치들과 기준 이상으로 겹치지 않았다. 두 조건 모두 기존과 같은 작은 칼 98개·전체 129개·음성 오탐 1장·FP 박스 12개에 그쳐 확인셋을 열지 않았다. 이 결과의 범위는 이번 학습 구간에서 확인한 배경 위치다. 같은 위치에 추가 감점 설정을 적용할 근거는 확보하지 못했다. 완료 영수증 SHA-256은 `dfa3887acfedeabef54d4423bd110a4f0fd38b5a174c98f80f779308849b73e3`이다. ## B-ALT07-NATIVE-RESIZE 실행

축소·복원 모의 실험의 이득이 원본 타일에도 나타나는지 PC13 CPU Worker에 비교를 등록했다. 같은 D1 가중치, 원본 타일, CPU에서 기본 보간과 Lanczos·bicubic을 각각 비교한다. 두 대안은 모형 입력 크기로 한 번만 줄인 뒤 패딩하고, 박스를 타일 원좌표로 복원한 다음 기존 경계 필터와 NMS를 적용한다. 이전 CUDA 예측은 참조 지표로 보존한다. 튜닝셋에서 소형·전체 검출과 두 오탐 지표를 악화시키지 않고 검출 2개 이상을 추가하거나 음성 오탐 1장 또는 전체 FP 2개 이상을 줄였을 때만 선택한 한 방법과 같은 CPU 대조군을 개발 확인셋에 적용한다. [실험 코드](../../../tools/p430_native_resize_pilot.py)

Worker 완료 영수증과 실제 결과 파일의 SHA-256 `e1630f675611ac6552b377d668664958460835bcbd14a5ca2523632022db44e2`가 일치했다. 298장 튜닝셋에서 고른 각 운영점의 결과는 다음과 같다.

| 보간 | 작은 칼 TP | 전체 TP | 음성 오탐 프레임 | 전체 FP 박스 | AP50 | AP50–95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 기본 CPU 대조 | 84 | 113 | 1 | 10 | 83.51% | 38.47% |
| Lanczos | 83 | 112 | 1 | 10 | 82.42% | 40.23% |
| Bicubic | 84 | 113 | 1 | 10 | 83.53% | 40.49% |

Lanczos는 두 검출 건수가 줄었다. Bicubic의 AP50–95는 2.02%p 올랐고 고정할 운영점의 검출과 두 오탐 건수는 대조와 같았다. 사전 운영점 개선 기준을 통과한 보간 후보가 없어 개발 확인셋을 열지 않았다. D1 기본 보간을 기준으로 유지한다.

## B-ALT01-MOBILENET-PILOT 비교 조건

HOG에서 쓰던 MIX70 후보를 그대로 이용해 RGB 기반 특징이 검출 점수에 보완 정보를 주는지 확인한다. DCR의 별도 크롭 분류를 참고하되, 영상 내 작은 물체가 실제로 구분되는지는 개발 자료로 판단한다. 공식 ImageNet 가중치가 있는 MobileNetV3-Small을 고정하고 균형 로지스틱 선형 분류기만 학습한다. [DCR](https://arxiv.org/abs/1810.04002) · [MobileNetV3](https://arxiv.org/abs/1905.02244) · [TorchVision 가중치](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.mobilenet_v3_small.html)

## 프레임별 전처리 선택의 튜닝 상한

ALT-07 저장 예측 3종을 튜닝 298장의 입력 순서와 해시로 확인했다. 기본 예측은 A0와 바이트 단위로 일치했다. 입력을 2배 축소 후 bicubic 또는 Lanczos로 복원한 두 조건의 합집합이 추가한 기본 미검출 후보는 3개였고, 모두 비소형 칼이었다. 각 방식의 기존 임계값을 고정한 채 프레임마다 정답을 아는 이상적인 선택기가 고른 상한은 전체 130/161, 소형 94/105, 음성 오탐 1/137, 전체 FP 박스 8개였다. 최고 단일 방식과 비교해 전체 검출 상한이 4개 늘고 작은 칼 상한은 같아 전처리 선택기를 구현하지 않는다. 해당 수치는 튜닝셋의 이론적 상한이다.

## 저점수 양성 타일 재표집

`A-MIX70-POS-MINE`과 `A-MIX70-POS-TRAIN`은 검수된 P430 학습 양성의 상대적 난이도가 검출에 미치는 영향을 시험한다. OHEM의 어려운 표본 선별 동기를 참고하고, 이번 실험에서는 저장된 MIX70 점수와 검수 라벨을 사용한다. 원래 MIX70이 학습했던 영상의 표본이 포함되므로 독립 자료 기준의 난이도 평가와는 구분한다. [OHEM 원 논문](https://arxiv.org/abs/1604.03540)

- 학습 전용 검수 양성 중 GT 박스가 하나이고 기존 승인 타일이 있는 사례를 사용한다. 동일 원본 영상과 정답 박스 짧은 변 크기 구간(`<8`, `8–16`, `16–32`, `≥32`px, 960×540 환산)에서 저점수 하위 25%를 후보로 고르고 동일 원본에서 5초 간격을 유지한다.
- 동일 원본·크기 구간에서 점수가 중앙값을 넘는 양성 타일의 학습 추출분을 10%까지 교체한다. 저점수 원본 1장당 epoch에 최대 두 번 더 추출한다. 기존 D0·seed·12 epoch·배치·LR과 출처별 예산 5,734/1,638/820, 기존 양·음성 및 전체·타일 추출 수를 유지한다.
- 먼저 저장 예측·학습 이미지·라벨·기존 타일 연결과 실제 교체 장수를 확인한다. 학습 결과의 후보·임계값은 튜닝에서 정한다. 공통 개발 확인에서는 D1과 MIX70의 동일 6타일 설정과 비교한다. [등록 목록](../../../configs/training/p430-overnight-queue.json)

PC13 첫 선별 시도는 공유 스냅숏에 로컬 HOG 완료 영수증이 없어 자료 처리 전 종료했다. 실패 영수증을 보존하고 Worker가 합친 실행 스냅숏을 사용해 `A-MIX70-POS-MINE-R1`을 완료했다. 검수 학습 761장의 저장 예측에서 승인 타일이 있는 단일 칼 양성 326개를 대조했다. 하위 25% 후보 78개 중 시간 간격 적용 후 41개를 남겼고, 같은 촬영·크기 구간의 중앙값 초과 양성 161개를 교체 대상으로 고정했다. 완료 결과 SHA-256 `fdf8fcb372623e1810975c63fffb16f8b5b1ef855dae251b2ce13da0eeffd23c`를 PC13 원본 및 PC12 수신 파일과 대조한 뒤 PC12의 기존 큐에 학습을 등록했다. P430 단위 테스트 51건과 컴파일을 확인했다.

PC12에서 12 epoch와 공통 개발 확인을 완료했다. epoch당 40~44개를 교체했고 튜닝에서 `epoch3.pt`를 선택했다. 개발 확인에서 작은 칼 39/58, 전체 84/140, 음성 오탐 7/147, 전체 FP 박스 43개, AP50 58.68%, AP50–95 20.40%를 기록했다. 기존 MIX70보다 검출과 오탐 박스 수가 악화돼 후보로 올리지 않았다. 영수증 SHA-256 `139502326f35242bdb948a0e5bd453a439e8f508510fa4c369c27ec546d91a39` 및 가중치 SHA-256 `dc9bc65c10413826cdfde13f8c5626626508797c630f93e2fbf4ad31e9cd77e0`을 대조했다.

## 촬영 원본을 분리한 교차 학습

PC12 첫 두 건은 기존 릴리스 기준 폴더에 타일이 없어 학습 전에 종료했다. 기존 승인 원본에서 누락된 타일 쌍을 재생성하고 이미지·라벨 해시를 대조하는 사전 검증을 재사용했다. 원래의 실패 기록과 승인 데이터는 보존했다. PC14 SSH 복구 및 큐 Worker 가동 후 두 실험을 병행했다. 두 실험은 D0 초기화, 같은 출처별 추출 예산, 12 epoch, 동일 평가 규칙을 사용한다. 임계값을 고르는 튜닝 자료는 학습에 사용한 촬영 원본의 별도 구간이며, 개발 확인은 반대 촬영 원본으로 구성했다. 11/24 독립 자료는 사용하지 않았다.

## 저대비 프레임의 D1 전역 대비 대조

두 촬영의 학습 전용 표본에서 밝기 표준편차의 중앙값은 11/17 약 55, 11/19 약 31이었다. 장면 구성도 달라 그 차이만으로 누락의 원인을 확정할 수 없다. 조건부 전처리 연구의 각 프레임 통계에 따른 적용·생략 원리를 참고했다. 여기서는 통계 한 개와 전역 픽셀 변환 한 개로 범위를 고정했다. [조건부 영상 전처리 연구](https://www.mdpi.com/2076-3417/16/15/7635)

PC12 `B-ALT12-GLOBAL-CONTRAST`는 동일 D1·6타일·0.001 후보 하한의 원본 조건과 960×540 환산 회색 표준편차가 40 미만인 프레임만 보정하는 조건을 비교한다. 평균 밝기를 중심으로 표준편차 55를 목표로 하며, 이득을 1.6배로 제한한다. 두 조건의 운영 임계값은 기존 규약으로 튜닝에서 결정한다. 11/19 TP가 2개 이상 증가하고 전체 TP를 유지하며 작은 칼 손실 1개 이하·음성 오탐 1장 이하인 경우에만 확인셋을 사용한다. 양쪽 튜닝과 고정 설정 확인을 같은 평가기로 실행한다. 11/24 자료는 사용하지 않는다.

실행기·D1 가중치·기존 타일 검출 코드의 해시를 대조하고 PC12에서 CLI 기동을 확인했다. 로컬에서 저대비·고대비·단색 합성 입력과 P430 테스트 51건을 확인했다. PC12 CUDA 큐에서 선행 교차 학습 완료 후 착수한다.

PC12 첫 시도는 오래된 실행 폴더의 `UltralyticsBackend`에 `predict_batch`가 없어 수치 산출 전에 종료했다. PC12·PC14에 커밋 `09e189f`의 배치 어댑터를 맞추고, 두 호스트에서 같은 D1의 합성 프레임 6타일·단일 크롭 CPU 추론을 확인했다. PC14의 기존 Worker는 시작할 때 한 번만 큐를 읽었다. 유휴·자식 작업 부재를 확인한 뒤 같은 커밋의 재로딩 지원 코드로 교체했다. PC14에서 `A-D1-PREFILTER-PARITY`의 GPU 실행과 `B-ALT01-ONE-CROP`의 대기를 확인했다.

PC12 재시도 `B-ALT12-GLOBAL-CONTRAST-R1`은 튜닝에서 완료됐다. 11/19는 83/111→64/111, 양쪽 합계는 전체 113/161→94/161, 작은 칼 84/105→65/105였다. 음성 오탐은 1/137로 같았다. 이 설정의 전역 대비 보정을 개발 확인으로 넘기지 않았다. 완료 영수증 SHA-256은 `e98891594b5506596aea407ce38e630156c89405a066d040ea90f1469a31bf09`다. 이 결과는 연구실의 별도 대비 증강 학습 결과와 구분한다.

## D1 6타일 ONNX 변환 및 TensorRT 예비 시험

동일 가중치를 640×640 FP32, 고정 배치 6, opset 17로 내보냈다. 로컬 Windows CPU의 Ultralytics 8.4.152·PyTorch 2.14.0과 별도 경로의 ONNX 1.20.1·ONNX Runtime 1.23.2를 사용했다. 첫 ONNX는 형식 검사와 합성 추론을 통과했지만, 승인 튜닝 16장에서 PyTorch와 박스 수가 다른 프레임이 2장 있었다. 연결된 5개 박스의 최소 IoU는 0.7531, 최대 점수 차이는 0.3519였다. 첫 그래프 SHA-256 `8676b460d1c92341be7acc8db059bbf09db28a84d45351b1ac1f06b5ad760e39`와 실패 결과 해시 `90f7b4b190ac45666a18e5a48155dec095e4619c7aff6d4322ea96eee5937f45`를 보존했다.

D1 PyTorch의 검출 헤드는 `end2end=False`였다. 설치된 exporter의 `nms=False`가 내보낸 헤드를 `end2end=True`로 바꾸는 것을 메타데이터·소스에서 확인했다. 두 번째 ONNX는 `nms=None`으로 기존 헤드를 유지한다. 그래프 검사와 합성 추론에서 `6×5×8400` 출력이 확인됐다. 동일 승인 튜닝 16장에서는 모든 박스 수가 일치했고 6개 박스의 최소 IoU는 0.999997, 최대 점수 차이는 0.00000072였다. 두 번째 그래프 SHA-256은 `a1b7ada3f8f5576316997ea60f42706d0f3a7157e32540b6d2c16145984c9b3f`, 표본 비교 SHA-256은 `8bbd9dd332326e4e4f1910499c3958b03e6c89fdbbf4608c76917b3560457aef`이다. [Ultralytics 모델 내보내기](https://docs.ultralytics.com/modes/export)

Orin의 L4T 39.2.0에서 TensorRT 10.16.2.10·CUDA 13.2 공식 패키지 후보를 확인했다. 첫 그래프로 예약한 독립 Worker는 파일 시험 잠금 대기 중에 중단했다. 다운로드·빌드 전 중단 영수증을 남겼다. 두 번째 그래프의 개발 표본 비교를 통과한 뒤 동일 잠금의 별도 `d1-tensorrt-fp16-v2` Worker를 시작하고 그래프·실행기 해시를 대조했다. J 파일 시험 종료 후 잠금 획득과 첫 패키지 해시 통과를 관찰했다. 사용자의 실행 디렉터리에서 패키지 해시 대조·엔진 변환·합성 처리를 수행한다. 시스템 패키지와 라이브러리를 변경하지 않는다. 개발 정답·실시간 영상·11/24 독립 자료는 변환에 사용하지 않는다. [NVIDIA JetPack 7.2 구성](https://developer.nvidia.com/embedded/jetpack/downloads/archive-7.2)

다운로드한 패키지 8개의 SHA-256을 일치 확인했다. Python 바인딩 실제 위치인 `runtime/usr/lib/python3.12/dist-packages`를 반영해 10.16.2.10을 로드하고 동적 라이브러리 누락이 없는지 검사했다. `trtexec`은 승인 ONNX를 파싱했으나 FP16의 최적화 수준 2와 0에서 동일한 KTM 합성곱 셰이더 단언 오류로 종료했다. 두 로그를 각각 보존했다. 더 높은 FP16 탐색 대신 작업 경로를 분리해 FP32, TF32 비활성, 최적화 수준 0, 보조 스트림 0으로 비교를 시작했다. 같은 계열 장치에서 다른 ONNX의 비슷한 로그를 보고한 공개 사례는 별도 모델과 소프트웨어 조합이다. [NVIDIA 빌더 최적화 문서](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/builder-performance.html) · [장치별 재현 보고](https://forums.developer.nvidia.com/t/jetson-orin-nx-8gb-hard-reboots-during-tensorrt-engine-build-on-fresh-jetpack-7-2-1-deepstream-9-1/382905)

엔진 변환과 합성 추론이 성공하면 승인 개발 JPEG 24장을 사용해 D1 PyTorch와 엔진을 교차 순서로 재생한다. 고정 출력 임계값 0.2883733511과 사전 필터 0.15, 같은 사람 검출기·B3·모의 경보를 적용한다. 같은 클래스 박스를 일대일로 대조하고 최소 IoU 0.95·최대 점수 차 0.02와 동일 경보 시점을 요구한다. 비교는 장시간 작동 및 P430 실시간 시험과 구분한다.

FP32 엔진 변환과 `trtexec` 합성 추론은 종료 코드 0으로 완료됐다. 24장 짝 비교에서 각 엔진 반복의 47개 박스가 대응했고 경보 전이와 박스 수가 일치했다. 최소 IoU는 0.9999986, 최대 점수 차는 0.00000048이었다. 전체 처리 지연 p95는 PyTorch 216.66 / 220.41 ms, TensorRT FP32 232.09 / 239.45 ms였다. 이 실행에서는 가속 이득이 없어 기존 PyTorch를 유지한다. 짝 비교 결과 SHA-256은 `b3fd39b1a7222d8b6e63e97626419ac02e3769281869005b99f08c15a009104f`다.

### PyTorch 칼 검출만 FP16

같은 D0 학습 경로의 D1과 PC14 대조군 `ema-batch-0512.pt`를 각각 0.5로 평균낸 단일 검출기 시험을 시작했다. 앞 체크포인트는 같은 튜닝 규칙에서 121/161·작은 칼 90/105·음성 0/137이었고 FP 박스는 22개였다. 구조와 클래스, 텐서 키·형상·자료형을 대조하고 부동소수점 파라미터·버퍼만 평균한다. 동일한 튜닝 298장과 오탐 상한을 사용하며 원래 체크포인트는 별도 보관한다. 평균 검출기는 같은 6타일을 한 번 추론한다. 정확도와 장비 실행 시간은 각각 실측한다. ## 4K HEVC 파일 수신 경로 예비 시험

기존 1080p JPEG 장시간 시험에는 4K 압축 영상 처리 부하가 빠져 있다. PC13의 원본 개발 영상에는 SSH로 도달하지 못했다. 승인 튜닝 JPEG 24장을 해시 대조하고 각 이미지를 4K 프레임 중앙에 그대로 배치했다. 바깥 영역은 회색으로 채우고 GStreamer x265로 3840×2160·25 FPS·200프레임 HEVC 파일을 생성했다. 파일 SHA-256 `01d50d203fd57afff725ece75fad738014847e0775dbf7fb07725a16d795cb21`. 정지 이미지의 반복과 인공 테두리는 실제 P430 장면의 복잡도를 재현하지 못한다. 11/24 자료는 사용하지 않았다.

Orin 25 W에서 해당 파일을 초당 25프레임으로 공급했다. `RTSPFrameSource`의 큐 크기 1과 실기기 J 측정 함수, D1 FP16 6타일·사람 FP32·B3·모의 경보를 재사용했다. 측정은 로컬 `read()` 시작부터 판단·경보·스냅샷 인코딩까지다. 네트워크와 물리 경보는 이번 시험 범위 밖이다. 첫 시도 `d1-file-4k-hevc-pilot-v1`의 예열은 206/240 유효 슬롯(3.43 FPS), p95 310.56 ms였다. 인코딩과 재생의 합이 단일 실행 제한 270초에 이르러 본측정 영수증은 작성되지 않았다. 종속 하드웨어 시도는 이 종료 상태를 확인하고 재생 전에 종료했다.

인코딩에 성공한 동일 파일을 SHA-256으로 고정하고, 파일 생성과 분리한 `d1-file-4k-hevc-sw-v2`를 시작했다. 예열 60초와 본측정 60초로 같은 조건을 다시 확인한다. `d1-file-4k-hevc-hw-v2`는 Orin의 같은 잠금에서 소프트웨어 완료를 기다린다. 본측정이 유효 3.8 FPS·누락 5% 이하·p95 250 ms 이하·경보 오류 0 기준에 미달할 경우에만 동일 파일로 `nvv4l2decoder` 경로를 비교한다. 결과는 작업별 `exit.json`과 `result.json`에 기록된다. [NVIDIA의 HEVC 하드웨어 디코딩](https://docs.nvidia.com/jetson/archives/r39.2.2/DeveloperGuide/SD/Multimedia/AcceleratedGstreamer.html)

### FFmpeg의 요청 프레임 BGR 변환

같은 4K 소프트웨어 디코더의 `grab()`은 원래 25 FPS로 수행하고, 판단 스케줄러가 요청한 시점에 최신 프레임만 `retrieve()`로 BGR 변환했다. FFmpeg 캡처는 한 스레드에서 관리하고 반환 큐의 최대 깊이는 1이다. `read()` 경로와 같은 프레임 번호 10개를 대조해 모든 BGR 픽셀이 일치했다. 첫 시도에서 파일 반복 시 `cv2` 참조 범위 오류가 발생했다. 해당 소스를 고쳐 새 작업 ID `d1-file-4k-hevc-demand-bgr-v2`에 기록했다. [OpenCV의 grab/retrieve 입력 경로](https://docs.opencv.org/4.10.0/d5/dc4/tutorial_video_input_psnr_ssim.html)

재시험은 종료 코드 0이었다. 예열·본측정 120초 동안 3,000프레임을 디코딩하고 448장만 BGR로 변환했다. 본측정 60초는 유효 **240/240 슬롯**, **4.00 FPS**, 누락·동작 오류 0이었고 읽기 시작→경보 p95는 **329.06 ms**, 큐 대기 p95는 **80.20 ms**였다. 기존 `read()`의 305.50·58.19 ms보다 각각 23.55·22.01 ms 늘었다. 요청 경로의 단계별 p95는 디코딩과 대기 62.80 ms, 디코딩 후 변환 대기 34.37 ms, BGR 변환 49.00 ms, 큐 전달 0.50 ms, 탐지 199.12 ms, 판단·출력 74.15 ms였다. 같은 프레임의 단계별 값을 기록했으며 표에 나열한 p95를 합쳐 전체 지연으로 계산하지 않았다. 이 경로는 250 ms 지연 기준에 미달해 적용을 보류한다. 파일·장비·모델·설정 일치를 확인했다. 결과 SHA-256 `1c53922a0e0e2b276dee921998f07775a8ca5299ad2119d05394501df75ab3ab`. 11/24 독립 평가 자료는 사용하지 않았다.

### 같은 BatchNorm 절차를 적용한 단독 가중치 대조

원래 D1 및 블러 `epoch3.pt`에 동일한 승인 학습 입력 128개와 BatchNorm 순전파 16회를 적용했다. 각 고정 모델의 원래 학습 파라미터와 114개 BatchNorm 층을 대조했다. 학습 파라미터 변경은 0개다. 기존 Orin FP16·6타일·하한 0.001로 승인 튜닝 298장을 평가했다. 확인셋 진입 기준은 음성 오탐 ≤1/137·FP 박스 ≤9, 통계 재계산한 50% 보간 대비 두 촬영·합산 검출 유지와 합산 전체 +3 또는 작은 칼 +2로 사전 고정했다.

### 프레임 내 경쟁 후보를 사용한 점수 보정

Orin이 학습 프레임 761장의 후보 저장을 종료 코드 0으로 끝냈다. `train.jsonl` SHA-256 `d293c9571cac5ba001a5546bda5eaac5b143c01bcae4cfd53aa5f73dae0a5508`를 기존 학습 라벨·계획과 대조했다. 이 예측과 승인 튜닝 예측이 같은 FP16 가중치·후보 하한에서 생성됐고 프레임 ID가 겹치지 않음을 확인했다.

프레임 내 오탐이 여러 곳에서 높은 점수를 얻는 경우를 구분하기 위해 원래 logit과 공간적으로 분리된 가장 높은 다른 후보와의 logit 차이를 사용했다. 비교 후보는 점수 상위 8개 중 IoU 0.10 미만이며, 분리된 후보가 없으면 점수 0.001을 대입한다. 학습 양성은 정답 IoU 0.50 이상인 후보 중 가장 높은 점수, 학습 음성은 사람이 칼 부재를 확인한 프레임의 가장 높은 점수다. 촬영×양성 여부의 네 그룹마다 프레임 해시로 정렬한 45개씩을 뽑아 총 180개로 기존 로지스틱 적합을 실행했다. 추론 때는 촬영 ID를 사용하지 않고 각 프레임의 기존 예측만 읽는다. 박스와 탐지기 가중치는 고정했다.

## FFmpeg 디코더 스레드 수에 따른 4K 지연

같은 Orin Nano 25 W에서 승인 개발 JPEG를 중앙에 배치한 4K·25 FPS HEVC 파일을 사용했다. D1 FP16 6타일·후보 하한 0.001, 사람 FP32, B3, JPEG 인코딩을 포함한 모의 경보, OpenCV 연산 스레드 2개 및 판단 주기 4 Hz를 유지했다. FFmpeg 디코더 설정만 2→1→4개 순으로 바꿔 각 20초 예열 후 20초를 측정했다. 각 캡처에서 적용된 스레드 값을 확인했고 첫 24개 디코딩 프레임의 BGR 해시가 세 설정에서 일치했다.

| FFmpeg 스레드 | 읽기·디코딩·BGR p95 | 큐 대기 p95 | 경보 없는 프레임 p95 | 전체 p95 | 모의 경보 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 73.32 ms | 60.77 ms | 288.34 ms | 307.24 ms | 4 |
| 1 | 90.84 ms | 73.40 ms | 332.36 ms | 336.18 ms | 2 |

모든 실행은 80개 슬롯을 처리해 유효 4.00 FPS, 누락·오류 0건이었다. 4개일 때 읽기와 큐 대기는 짧았지만 탐지 p95는 199.17 ms로 2개 설정의 198.87 ms와 가까웠다. 슬롯마다 선택된 영상 프레임과 모의 경보 횟수가 달라 전체 p95에 포함된 JPEG 비용도 달랐다. 4개 설정에서 JPEG에 실제로 걸린 시간만 프레임별로 빼도 추정 p95는 268.99 ms였다. 세 설정 모두 파일 예비 시험의 250 ms 기준에 미달했다. `d1-file-4k-hevc-decode-threads-v1`은 종료 코드 0으로 완료했다. 결과 SHA-256은 2개 `f7609a5050b2cbe32327a27838f9474334d1b45c203759c75849e1a6a7528cd2`, 1개 `fcea9ad64677a8859f5b69070c39a20cdf4e59986057977148fd102eaf961f1d`, 4개 `616acec529d2b2cf16069983df960e0ac2acecb364f140ed926ac00968f8745d`다.
